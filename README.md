# Архитектура ИС оценки битых автомобилей (Техническое задание для разработки)

## 1. Общие сведения и принципы

**Назначение:** Автоматизация процесса оценки остаточной стоимости битых автомобилей для компаний-скупщиков. Система рассчитывает потенциальную выручку от продажи уцелевших запчастей и формирует рекомендацию по цене выкупа.

**Ключевые архитектурные принципы:**
1. **Асинхронность:** Оценка — это фоновая задача (Celery), так как парсинг сайтов и работа ИИ занимают время. Клиент получает статус и результат по API.
2. **Модульный монолит:** Backend (FastAPI) выступает единой точкой входа и оркестратором. Тяжелые модули (ИИ, парсер) вынесены в отдельные воркеры.
3. **Прозрачность (Explainable AI):** Каждая цена сопровождается ссылкой на источник. Оценка ИИ содержит текстовое обоснование и веса факторов.
4. **Безопасность внешних данных:** Frontend общается только с Backend. Backend инкапсулирует доступ к внешним сайтам (Авито, Авто.ру) и ИИ-моделям.
5. **Человеко-ориентированность:** Система выдает рекомендацию, финальное решение о цене принимает механик.

## Системные требования

*1. Требования к системе в целом:*
* Система должна обеспечивать круглосуточный доступ (99.9%).
*	Система должна поддерживать ролевую модель (Руководитель, Механик, Наблюдатель).

*2. Требования к функциям:*
*	Прием фото (до 20 шт.) и текстового описания повреждений.
*	Опциональное определение авто по VIN.
*	Выдача списка деталей с оценкой пригодности (уверенность ИИ, обоснование).
*	Сбор цен с Авито и Авто.ру, расчет медианы.
*	Расчет итоговой стоимости: Сумма медиан − стоимость разборки.
*	Формирование JSON-отчета (без истории снимков, только даты получения).
*	Ежедневный мониторинг цен и генерация рекомендаций.

*3. Требования к надежности и безопасности:*
*	Доступ по JWT-токенам.
*	Хранение данных в соответствии с настраиваемым сроком (1/7/30 дней).
*	Защита от парсинг-блокировок (rate limits, прокси).

*4. Требования к прозрачности (Explainable AI):*
*	Каждая цена должна сопровождаться ссылкой на источник.
*	ИИ должен возвращать факторы, повлиявшие на решение (пробег, зона удара).

## 2. Компоненты и стек технологий

```text
[React SPA] 
     │ (REST API)
     ▼
[Nginx / API Gateway]
     │
     ▼
[Backend API — FastAPI/Python] ──── [PostgreSQL 16]
     │      │      │                [S3/MinIO (Фото)]
     │      │      └── [Redis + Celery (Очередь задач)]
     │      └── [Calculator Module] (Синхронный расчет)
     ▼
[Celery Workers]:
  ├── AI Worker (CV + LLM) 
  ├── Parser Worker (Авито, Авто.ру)
  ├── Monitoring Worker (Ежедневный пересчет)
  └── Retention Worker (Очистка данных)
```

| Компонент | Стек | Назначение |
| :--- | :--- | :--- |
| **Frontend** | React 18+, TypeScript, Vite | SPA с интерактивной таблицей, загрузкой фото и JSON-экспортом. |
| **Backend API** | Python 3.11+, FastAPI, Uvicorn | Аутентификация, RBAC, оркестрация, REST API. |
| **Очередь** | Celery 5+, Redis 7 | Асинхронная обработка тяжелых задач (ИИ, парсинг). |
| **AI Worker** | Python, OpenCV, LLM (через API) | Анализ фото/описания, определение пригодных деталей. |
| **Parser Worker** | Python, HTTPX / Playwright | Сбор актуальных цен с Авито и Авто.ру. |
| **База данных** | PostgreSQL 16 | Метаданные, оценки, офферы, аудит, справочники. |
| **Хранилище** | S3-совместимое (MinIO) | Хранение фото (с автоудалением по TTL). |
| **Инфраструктура** | Docker, Docker Compose, Nginx | Контейнеризация, API Gateway, SSL. |

## 3. Роли и права доступа (RBAC)

| Роль | Описание | Права |
| :--- | :--- | :--- |
| **`head`** (Руководитель) | Владелец компании или директор | Управление пользователями и настройками (срок хранения, регион по умолчанию). Просмотр всей статистики и оценок. Управление источниками цен. |
| **`mechanic`** (Механик/Оценщик) | Основной пользователь | Создание оценок (загрузка фото, VIN, описание). Редактирование предложенных деталей, ввод стоимости разборки. Экспорт JSON. |
| **`senior_mechanic`** (Старший механик) | Бригадир смены (опционально) | Все права `mechanic` + просмотр и корректировка оценок других механиков своей смены. |
| **`observer`** (Наблюдатель) | Партнер или аудитор | Только чтение оценок и статистики (без права изменения данных). |

## 4. Бизнес-логика и расчет

**Основная формула:**
`Рекомендуемая стоимость = Σ (Медианных цен пригодных деталей) − Стоимость работ по разборке`
*(Маржа компании в формулу не закладывается, она обсуждается на этапе торга).*

**Правила формирования цен (Fallback):**
*   **Порог достаточности:** минимум **3** валидных объявления с Авито/Авто.ру.
*   **≥ 3 объявлений:** берется медиана, флаг `ok`. Включается в итог.
*   **1-2 объявления:** берется медиана, флаг `low_data_confidence`. По умолчанию **не включается** в итог до подтверждения механиком.
*   **0 объявлений:** справочная цена (Каталожная цена × КЛН). Флаг `no_market_price`. **Не включается** в итог автоматически.

**Учет ресурса деталей:** ИИ сверяет пробег с правилами износа (например, АКПП для конкретной модели требует замены после 100 тыс. км). Если правило срабатывает — деталь помечается как непригодная.

## 5. Схема данных (Core Entities)

Для старта разработки необходимы следующие сущности (PostgreSQL):

*   **`companies`**: `id`, `name`, `retention_days` (1/7/30), `default_region` (по умолчанию "Екатеринбург").
*   **`users`**: `id`, `company_id`, `role`, `email`, `password_hash`.
*   **`vehicles`**: `id`, `vin` (nullable), `make`, `model`, `year`, `source` (vin/photo/manual).
*   **`assessments`**: `id`, `company_id`, `user_id`, `vehicle_id`, `status` (queued/processing/calculated/failed), `region`, `mileage`, `disassembly_cost`, `recommended_total`.
*   **`assessment_items`** (Детали): `id`, `assessment_id`, `part_name`, `suitability` (usable/conditionally), `ai_confidence`, `ai_reason`, `ai_factors` (JSONB), `median_price`, `offers_count`, `data_quality_flag`, `included_in_total` (bool).
*   **`price_offers`**: `id`, `assessment_item_id`, `source` (avito/autoru), `price`, `url`, `published_at`, `fetched_at`.
*   **`kls_coefficients`**: `id`, `part_group`, `coefficient` (справочник коэффициентов ликвидности для fallback).
*   **`audit_log`**: Логирование всех действий пользователей.

## 6. Ключевые Endpoints API

| Метод | Endpoint | Описание |
| :--- | :--- | :--- |
| `POST` | `/api/v1/auth/login` | Получение JWT. |
| `POST` | `/api/v1/assessments` | Создание оценки (multipart/form-data: фото, VIN, пробег). Возвращает `assessment_id` и статус `queued`. |
| `GET` | `/api/v1/assessments/{id}/status` | Polling статуса обработки (catalog -> ai -> parser -> calculated). |
| `GET` | `/api/v1/assessments/{id}` | Получение полного результата (таблица деталей, расчет). |
| `PATCH` | `/api/v1/assessments/{id}/items` | Ручная корректировка (включить/исключить деталь, переопределить цену). |
| `GET` | `/api/v1/assessments/{id}/export` | Выгрузка в JSON (schema 1.1). |
| `GET` | `/api/v1/monitoring/recommendations` | Список рекомендаций по изменению цен (для Head). |
